### 修复的核心 bug（关键）

**后端正则贪婪匹配，发布功能实际上完全没生效。**

`const cityMatch = p.match(/^\/api\/cities\/(.+)$/)` 对 POST `/api/cities/成都/guides` 会把城市名解析成 `成都/guides`。
→ 发布写进去的 `cityName` 是 `成都/guides`，而读取按 `成都` 查 → **永远读不到**。

修复：拆成两条路由，且把 `[^/]+` 的 `/guides` 路由放在单城市路由**之前**：
```js
const cityGuidesMatch = p.match(/^\/api\/cities\/([^/]+)\/guides$/)  // POST/PUT upsert + DELETE 撤回
const cityMatch = p.match(/^\/api\/cities\/([^/]+)$/)               // GET 单城市
```
注：`pathname` 不解码，中文是 `%E6%88%90%E9%83%BD`，所以 `[^/]+` 不会被城市名里的字面 `/` 影响（`%2F` 不含 `/`）。

### 三、踩到并修掉的三个真 bug（都是这次用测试逼出来的）

1. **墓碑 30 天 TTL 会制造复活窗口** —— 一台离线两个月的设备上线会把已删记录整批推回。
   去掉 TTL，只按条数封顶。
2. **「待推送」只看 Trip.updatedAt** —— 加一笔账单只给账单打戳，行程本身没变，
   于是账单永远推不上去。**不能改成「改子记录就刷 Trip.updatedAt」**，那会让

   解法：新增独立的 `sync.localAtOf[tripId]` 本地脏标记，与参与合并的 updatedAt 解耦；
   所有用户改动统一以 `commit(tripId)` 收尾（而不是 `persist()`）。
   并用 `grep -nE "this\.(persist|commit)\("` 核对过每一处调用点。
3. **列表默认过滤掉已删空间 → 别的设备永远学不到「行程被删了」**，会一直留陈旧副本。
   改成默认返回已删空间（带 `deleted:true`），拉取端才能收敛。
4. **`applyServerDoc` 合并时从「本地」起手** —— 「本地有、服务端没有」既可能是
   「服务端删了」也可能是「本地还没推」，必须靠**服务端回传的墓碑**区分。
   补 `serverTombstones` 参数后，删除才能真正传播到其他设备。

### Step 1 · 换 SQLite（完成）

`server/lib/store.mjs`（单文件 JSON）→ `server/lib/db.mjs`（SQLite），旧文件已删除。
**关键前提**：Node 22.22.2 的 `node:sqlite` 可直接 `require`，**无需 `--experimental-sqlite` flag**，
所以沙箱里 `npm install` 被拦也不影响 —— 依然零依赖。

表：`spaces`（元信息 + 列表用冗余投影 title/destination/日期）、`records`（实体，整条记录存 JSON）、
`tombstones`、`guides`。`PRAGMA journal_mode=WAL` + `synchronous=NORMAL` + `busy_timeout=5000`。

- 存入 `DATA_DIR/travel.sqlite3`（不再是 db.json）
- `saveSpace` 是**空间级事务**：DELETE+INSERT 只针对该空间，其他空间一个字节都不碰 —— 这才是相对「全库 JSON 重写」的真改进
- 列表走一条带子查询的 SQL，直接算出 `deleted` 与各集合 counts，**不加载文档**
- `isSpaceDeleted` 只在 db.mjs 定义一次，trips 路由 import 复用
- 旧 `db.json` 首次启动且库为空时自动导入，原文件 rename 成 `.migrated`（保留不删）
- 打包前先 patch `process.emitWarning` 屏蔽 `node:sqlite` 的 ExperimentalWarning，避免每次启动冒噪音

**踩到的 2 个真 bug（都写进 overview 了）：**

1. **`digestOf` 对顺序敏感**。原来直接 `JSON.stringify(space.doc)` + tombstones。
   旧 JSON 实现里墓碑顺序恰好等于插入顺序所以看不出问题；换 SQLite 后回读变成主键序
   （`kind` 排前的 `expense` 跑到最前面），**同一份墓碑集合算出不同指纹 → 假 changed → rev 乱涨**。
   修法：规范化后再算摘要 —— 数组按 id 排序、对象键按字典序排序（`stableValue` 递归）。
   这条同时修掉了旧实现的隐患：客户端提交顺序不同也会造成假 changed。
2. **迁移用了嵌套事务**。`migrateLegacyJson` 外面套 `tx()`，里面每次都调 `saveSpace` 又 `tx()`，
   SQLite 报 "cannot start a transaction within a transaction" → 带旧数据的实例直接起不来。
   修法：`tx()` 加 `inTx` 标记支持嵌套，内层直接复用外层事务，原子性由最外层负责。

顺手修的：`smoke.mjs` 第 264 行 `const join = await M(...)` **遮蔽了 `node:path` 的 `join`**，
导致同一个 try 块里后面所有 `join(...)` 全炸（`TypeError: join is not a function`）。已改名 `joined`，
并在原处留了注释警告。

**新增 17 条存储层断言**（smoke `[14]`，从 88 → 105）：
建库文件 / 不产生 db.json / 改 A 不动 B 的 rev / SIGTERM 优雅关闭后重启数据仍在
（内容、成员、分享码、攻略、凭码加入）/ 旧 JSON 导入（行程 + 成员 + rev + 攻略 + 旧码可用）/
旧文件归档为 .migrated / 再启动不重复导入。

调试经验：`bootStore` 原来用 `stdio: 'ignore'`，启动失败只给你一句「超时」，
改成 pipe 收集最后 4KB 输出并在超时时抛出 —— 上面那个嵌套事务的错就是这么看到的。

验证：后端 **105/105**、客户端 **36/36**、类型检查 + 构建通过。

### Step 2 · HLC 逻辑时钟（服务端 + 客户端，完成）

把「谁更新」从各设备的 `Date.now()` 换成 HLC `{t, c, n}`。
两侧：`server/lib/hlc.mjs`（有 `cap` 封顶）、`src/services/hlc.ts`（有 `observe` 封顶）。
客户端那半是这次新补的 —— 只有服务端有 HLC 的话，服务端拿到的仍是一个不可信的物理时间。

**四条设计结论（都是踩过之后才定的）：**

1. **编码用定长字符串** `TTTTTTTTTTTTTTT-CCCCCC-NNNNNNNN` → 字典序 == 三元组序，
   于是 JS 的 `cmpHlc` 与 SQL 的 `MAX()`/`>=` 结论天然一致，不用在 SQL 里写三段 OR。
2. **封顶只压 `t`，保留 `c` 与 `n`**。一度把整个三元组塌成同一个上界值，
   结果两条都超前的记录无法分先后 ——「后改的赢不了」。
3. **封顶只作用于比较，绝不改写存储**（最重要）。封顶值依赖 `now`；写回后同一条超前记录
   每次推送都被封到更大的值 → 每次都判 `changed:true` → `rev` 无限涨 → 所有客户端反复全量拉取。
   保持原值 ⇒「同一输入同一判定」，幂等才成立。中途还试过 SQL 侧 `MIN(hlc, capKey)`，一并删掉，
   封顶收回 JS 单点实现。
4. **`stamp()` 必须先做 receive**：取下一个戳前把本地时钟推进到已接受记录之后。
   否则服务端刚盖的删除墓碑可能**只因节点号小**就输给客户端记录，被判成「删后又改」，删除传不出去。

**这次最大的坑（症状极具迷惑性，务必记住）：**

客户端 `stamp()` 只写 `updatedAt`、不动 `hlc`，而 `applyServerDoc` 把服务端下发的 `doc.trip`
（**含 hlc 字段**）整条存进本地。编辑后再推送，服务端 `normHlc(raw.hlc, updatedAt)` 优先采信那个
**陈旧 hlc** → 比较结果既不算更新也不算冲突 → **编辑被静默丢弃**
（`applied.conflicts === 0`，标题纹丝不动，`rev` 也不涨）。

- 迷惑点：用 `/tmp/dbg-hlc.mjs` 发**不带 hlc** 的裸 HTTP 请求能正确复现 LWW（`conflicts:1`），
  走真实客户端流程却失败 —— 说明服务端算法没问题，问题在客户端带上来的数据。
- 定位手段：在 `backend.pushSpace` 打一行 payload 日志，看到
  `updatedAt=...510449` 而 `hlc.t=...509947`（正好是上一轮云端带回来的那个值），假设当场坐实。
- 修法两手，缺一不可：
  - 客户端建自己的 HLC（`src/services/hlc.ts`），状态持久化进 `SyncMeta.hlc`，
    收到云端数据时 `observe`、编辑时 `stamp`；`applyServerDoc` 的合并与墓碑判定全部改走
    `recordHlc` / `hlcAfter`，与服务端同一语义。
  - 服务端归一化一律走 `recordHlc(raw.hlc, updatedAt)`（`max(hlc, hlcFromTs(updatedAt))`）兜底，
    老客户端也不会再被吞。

**顺带挖出的同类 bug：`storage.readSync()` 是白名单式重建**（逐字段挑，不是展开后覆盖）。
新加的 `hlc` 字段如果不显式带出来，每次读取都会把它悄悄丢掉 → 冷启动后逻辑时钟从 0 起步
→ 所有编辑被判落后而丢弃，而本地一切正常。已补字段 + `normStoredHlc()` 校验（畸形的返回
undefined 让调用方重新起步），并加了 `[9]` 三条断言钉住。**以后往 `SyncMeta` 加字段必须同步改 readSync。**

**新增断言：** 后端 `[15]` 12 → 23 条（陈旧 hlc 兜底 / 编码字面量 / 字典序），总 124 → **136**；
客户端新增 `[0]` HLC 自检 8 条 + `[9]` 持久化 3 条，总 36 → **49**。
编码字面量在两侧各断言一次（同一组字面量），等于把「两端同一把尺子」钉死。

验证：类型检查 0 错、mp-weixin 构建 DONE、后端 **136/136**、客户端 **49/49**。

## Step 3 · 字段级合并（per-field LWW，完成）

（按记录比大小必然丢一边：后推的那份会把对方的改动整条盖掉。）

**新增文件**：`server/lib/lww.mjs` + `src/services/lww.ts`（孪生实现，各 158 / 165 行），
导出 `MERGE_META_KEYS` / `MAX_MERGE_FIELDS` / `dataKeysOf` / `fieldHlcsOf` / `withRecordHlc` / `mergeRecord`。
`server/routes/trips.mjs` 的 `mergeIntoSpace` 换成逐字段调用；store 新增 `stampFields(recs, fields?)`
（`stamp` 是它的简写）与 `ensureFieldStamps(tripId)`，14 处写路径全部精确到字段。

### 四条设计结论（都是踩过才定的）

1. **字段戳映射必须完整**。缺字段会退回记录级 HLC，而记录级 HLC = 各字段戳的**最大值**，
   会被别的字段顶高 → 「只改了预算」的客户端把没动过的标题也顶到新时刻 → 盖掉别人刚改的标题，
   **比记录级还糟**。修法：`ensureFieldStamps` 在 `commit()` 唯一收口处统一补全（只补不顶），
   写入路径再只顶本次改动的字段。
2. **`fieldHlcsOf` 里给显式列出的字段戳不能再套 `recordHlc` 兜底**。第一版套了，
   于是陈旧字段反过来盖掉别人。兜底**只**该发生在映射里根本没有这个字段时（老记录 / 老客户端）。
3. **平局口径：严格更晚才赢，相等保留 `base`**。两端的 base 都是「服务端那一版」
   （服务端 = 库里内容；客户端 = 刚拉下来的服务端版本、incoming = 本地含未推送改动），
   平局时两端都归到服务端的值，不会来回翻。两端必须逐字一致。
4. **记录级 `hlc` / `updatedAt` 一律由字段戳推导（max），不允许各自独立赋值**。
   记录级 HLC 只用于跟墓碑比「删后又改」，语义正是「最后一次被碰是什么时候」= 各字段戳的最大值。

### 客户端也必须做这一遍（真实数据丢失窗口）

本地有未推送改动（戳 H2）时拉下服务端新版本（别人改标题，戳 H3）；若按记录级比大小，
本地整条 H3 落败 → 本地那笔金额改动被覆盖 → 推上去时它已经不在了 → **改动丢失**。
所以 `applyServerDoc` 的列表合并也改走 `mergeRecord`（base = 服务端那版）。
`applied` 语义随之调整：`updated` = 至少一个字段被赢走；`conflicts` = 一个字段都没赢。

### 五个设计结论

1. **两套凭据正交**：共享密钥走 `Authorization`/`X-Api-Key`（部署级门禁），
   会话令牌走独立头 `X-Session-Token`（身份）。测试钉死「令牌塞进 Authorization 不生效」
   「只有身份没有共享密钥也进不来」。
2. **令牌无状态**：不建 session 表，校验 = 重算签名 + 查过期。代价是无法单独吊销，
   只能轮换 `SESSION_SECRET`；因此「登出」是纯客户端动作。
3. **归属分「有主 / 无主」**：无主空间（接账号体系之前的存量数据）**保持开放**，
   有主空间只认 owner / 成员。一刀切会把「群里那几个人一起记的账」当场锁死。
4. **认领必须显式且出示分享码**：自动认领 = 把「谁知道 id」静默升格成「谁拥有它」；
   只凭 id 就能认领则是抢行程的后门。只对真正无主的空间成立。
5. **`openid` 不进响应体**：列表不带 `owner_openid`，攻略对象不带 `author_openid`。
   「不放进返回对象」比「放进去再记得删掉」可靠。

### 踩到的两个坑（都是「测试静默失效」，比红灯更危险）

  `ensure` 与 `bootStore` 都是「目标端口已有服务就直接复用」，
  于是 `[14]` 的「重启后数据还在」跑在了别人的实例上 —— **断言照过，什么都没验到**。
  已挪到 8796 / 8797 并在注释里写明必须避开。

  A 登录会连带把 B、C 变成「已登录」，403 类断言永远测不到。
  修法：测试脚手架 `as(dev)` 时按该设备自己的身份重设令牌，补回真实环境「一个运行时一个 store」的隔离。
  （与 Step 3 的 `hlcClock` 单例是同一类问题：**模块级状态在多实例脚手架里会串台**。）

### 另一处顺带修的隐患

## Step 5 · WebSocket 实时同步（五步计划收口）

### 定位先写死，后面全是推论

> **实时是加速层，不是可靠层。** 消息丢了、连接断了、通知乱序了，都不影响正确性。

订阅响应里带每个空间当前的 `rev`，客户端拿它跟本地 `sync.revOf` 一比，对不上就补拉**那一个**空间。
Step 1–4 的「离线补推 + rev 比对 + 字段级合并」仍是唯一的正确性来源，实时只把等待时间从
「下次同步」压到毫秒级。这条取舍省掉了整个离线消息队列与序列号补漏机制。

### 新增文件

- `server/lib/ws.mjs`（约 570 行）—— RFC 6455 协议层：握手、帧编解码、掩码、三档长度、分片、控制帧约束。
  `createFrameParser` 是**纯状态机**（喂 Buffer 进、吐事件出，不碰 socket）。
- `server/lib/hub.mjs` —— 订阅中心，只认「连接」（有 `id` + `send`）。
  `add / remove / subscribe / unsubscribe / dropSubscribers / notify / stats / closeAll`。
- `server/lib/realtime.mjs`（约 450 行）—— 实时网关：upgrade 处理、首帧鉴权、订阅授权、心跳、消息限速。
- `server/lib/acl.mjs` —— 权限口径的**唯一定义处**（`spaceHasOwner` / `accessVerdict`），REST 与 WS 共用。
- `src/services/realtime.ts`（约 400 行）—— 客户端控制器（**工厂，不是单例**）。

### 为什么手写协议

沙箱 `npm install` 被 broker 拦掉，Node 内置只有 `http` / `net`，**没有 WebSocket 服务端**，
所以握手与帧编解码是自己写的。意外好处：纯状态机解析器让「TCP 把帧切在头部中间」
「一个 chunk 挤三个帧」「长度跨 7/16/64 位边界」这些真机难复现的情况，变成**逐字节喂入**的确定性断言。

### 八个设计要点

| 要点 | 结论 | 为什么 |
|---|---|---|
| 鉴权分两段 | 握手只做同源校验，令牌走首帧 `{t:'hello', token, key}`；`authGraceMs` 内没收到就关 4001 | `new WebSocket(url)` **不能自定义请求头**；令牌塞 URL 会进访问日志 / Referer / 浏览器历史 |
| 只推通知不推内容 | 只发 `{t:'update', id, rev, deleted, updatedBy}`，客户端自己拉那一个空间 | 合并逻辑只有一份（不会「REST 一套、WS 一套」慢慢漂移）；大行程改一个字段不广播整份文档 |
| 权限口径单一定义处 | `trips.mjs` 与 `realtime.mjs` 都调 `acl.mjs` 的 `accessVerdict` | 复制一份迟早漂移成静默越权。「无主空间保持开放」也一并继承 |
| 授权变更要撤销已有订阅 | `/claim` 时 `dropSubscribers` 踢非成员 + `unsubscribed{reason:'access-revoked'}` | 否则「认领前随手订阅过的人」继续收通知 |
| 排除「连接」而非「设备」 | 连接 id 由 `ready` 帧分配，客户端放进 `X-Conn-Id` 头 | 同设备两个标签页 `deviceId` 共享，按设备排除会让另一标签页收不到自己刚提交的改动 |
| 通知合并 | 窗口内（默认 80ms）同空间多次变化合成一条，`rev` 取最大；`except` 取**交集** | 连续输入的多次推送不打满连接；A、B 各发起一次时谁都不能被排除 |
| 心跳走应用层 `{t:'ping'}` | 判死 = 「连续两个周期没收到**任何**帧」；超时用 1001（可重连） | 小程序 `SocketTask` 不保证暴露协议层 pong；持续推数据的连接不该被误杀 |
| 首帧带完整订阅集合 | 逐条回 `subscribed{id,rev,deleted}` / `unsubscribed{reason}` | 比对 `rev` 即完成断线补偿，不需要额外补漏接口 |

### 踩到的坑（含一个 Step 4 遗留真 bug）

| 问题 | 后果 | 修法 |
|---|---|---|
| `close()` 先置 `closed=true` 再 `rawSend(关闭帧)`，而 `rawSend` 判了 `closed` | 关闭帧发不出去，对端只看到连接被强拆 | `rawSend` 只判 `socket.destroyed`；`send` 自己判 `closed` |
| `createWsConnection` 返回包装对象，而 `onMessage` 回调拿到内部描述符 | 网关挂的 `openid` / `helloReceived` 在另一个对象上 → `conn.send is not a function` → 进程退出 | 方法**挂回 `conn` 自身**、直接 `return conn` |
| `hub.notify` 合并分支 `cur.except = new Set(...)`（换引用） | flush 闭包捕获原对象 → 排除静默失效 | **原地** `delete`，不换引用 |
| `const conn = createWsConnection(...)` 构造期同步触发 `onClose` | 访问 `conn` 抛 TDZ `ReferenceError` | `let conn = null` + `if (!conn) return` |
| **Step 4 遗留**：CORS `Access-Control-Allow-Headers` 漏 `X-Session-Token` | 小程序不执行 CORS → 只在 H5/浏览器调试暴露：带身份的请求全失败、匿名照常，极难联想到 CORS | 补齐 `Content-Type,Authorization,X-Api-Key,X-Session-Token,X-Conn-Id,X-Request-Id` |
| `uni-mock.connectSocket` 用 `replace('http://localhost:8787', TEST_BASE)` | 实时地址是 `ws://` → 子串匹配不上、替换**静默失效** → 客户端实时断言全 `offline` | 新增 `rewriteHost()`，按 host 比对、协议无关 |

**这是第四次踩「模块级状态在多实例脚手架里串台」**（前三次：`hlcClock` / `syncTimer` / `backend.sessionToken`，
这次是「连接成了两个对象」与「实时控制器单例」）→ 一律 `WeakMap<store, …>` 或按调用点显式传参。

### 两条「断言写错」而非「实现错」

放宽容忍度是更坏的选择，所以都是改断言而不是改实现：

- 「重复推送」失败：`makeDoc(title, dt)` 每次现算 `Date.now() + dt`，实际推的是两份 `updatedAt` **不同**的快照
  → 服务端判 `changed=true` 是对的。修法：复用同一个对象。
- 客户端 T6「登出后收不到改动」：期望「本地不变」，实际被去抖触发的 `syncAll` 拉回来了 ——
  服务端**确实拒了**订阅（`anonymous-on-owned`）。修法：改成断言「没收到**实时通知**」+
  从服务端订阅回执确认拒绝记录（把临时探针转成正式断言 `subLog`），并写下
  「按 id 读取是开放的 —— 实时订阅不是机密性边界」这条已知边界。

### 1. CLI 服务端口默认关闭

交互式提示「请输入 y 确认开启」用管道喂 `y` 无效（不读 stdin），所以脚本化场景直接改配置更快。

- 设置文件：`~/Library/Application Support/微信开发者工具/<hash>/WeappLocalData/localstorage_<md5>.json`
  的 `security.enableServicePort`（同段还有 `security.port`，工具启动后会把它**改写成自己选的端口**）。
- 工具支持启动参数 `--enable-service-port`，但要求 `onAppOpen(argv, flag)` 的第二个参数也为真，
  **对已运行实例无效**（`open -a ... --args` 不向运行中实例投递参数；`open -n` 也不行）。
  → 必须**冷启动**一次，或直接改上面的 JSON。
- 设置文件**必须等工具退出后再改**，否则退出时会被内存里的旧值覆盖。
- 端口号写在 `~/Library/Application Support/微信开发者工具/<hash>/Default/.cli`，
  但工具运行中会改写这个文件（观察到 3799 ↔ 25365 来回变），**不要以它为准**：
  CLI 自己会打印实际端口（`✔ IDE server has started, listening on http://127.0.0.1:25365`）。
- 退出工具：AppleScript `quit` 会被拒（`-10004 权限违例`），`pkill -TERM` 1 秒内干净退出。

### 2. CLI 不接受游客 AppID（这条最坑）

报错是 `不存在此 AppID 请检查后重新输入`，看着像 AppID 填错，实际工具日志里写得很清楚：

```
[q.formatProject] [automation_game] formatProject reject tourist/empty appid { projectpath: ... }
```

**`formatProject` 在进项目之前就把 `touristappid` / 空 AppID 挡掉了**，与「AppID 真的不存在」
共用同一句话。试过把 `project.config.json` 的 appid 置空 → 同样报错，说明不是取值问题而是硬限制。

- 游客模式（`touristappid`）**只有 GUI 的「导入项目」能用**，GUI 会读 `project.config.json`，不用手填。

  没有「打开项目」的 URL 入口，这条捷径不存在。

### 坑 1 · WXSS 不支持通用选择器 `*`

`*{box-sizing:border-box}` 与 `.avatar-stack > * {...}` 都被 WXSS 编译器直接拒，报错信息只有一句
「编译 .wxss 文件错误」**且不附文件与行列号**，细节在模拟器控制台里，二十来个 wxss 只能靠猜。
用工具自带的 `wcsc -lc -o out.x app.wxss`（路径：`/Applications/wechatwebdevtools.app/.../wcc-exec/wcsc`）
可以直接拿到 `app.wxss(1:1828): unexpected token *`，于是能在源码里精确改。

注意一个直觉误判：`@media (prefers-reduced-motion: reduce)` **本身是合法的**，被拒的是它里面的 `*`。
别把「媒体特性不支持」当成结论 —— 用 `wcsc -sd '<css>'` 单独试一条就能确认。

修法（`src/styles/global.css`）：
- 去掉 `*` 重置，小程序端改成 `page,view,scroll-view,movable-area,...` 显式列出内置组件标签。
- `.avatar-stack > *` 改成 `.avatar-stack > .av`，在两处用到的位置把 `<AppAvatar>` 外层包一层 `<view class="av">`。
- 减弱动态效果的 `@media` 整段用 `/* #ifdef H5 */` 条件编译只下发 H5。

### 坑 2 · `uni.connectSocket` 不传回调时返回 `Promise`，不是 `SocketTask`

uni-app 约定：**不传 `success/fail/complete` 就把 API Promise 化**。于是 `next.onOpen` 是 `undefined`，
注册监听时抛 `TypeError`，异常一路穿出 `connect()` → `start()` → `startRealtime()` → **`onLaunch` 中断**。

后果链很阴险：
- 状态永远卡在 `connecting`，`onOpen / onMessage / onError / onClose` 一个都没触发。
- `onLaunch` 中断后所有依赖它初始化的逻辑（包括一个临时调试弹窗）也跟着失灵，
  让我一度怀疑是 UI 层问题。
- H5 与 `scripts/uni-mock.ts` 的 mock 都返回 `SocketTask`，所以 137 条客户端断言全绿也照样漏掉。
- 调试工具链（小程序控制台、模拟器面板、本地存储）都没直接暴露 Promise 化这点，
  最终是用裸 TCP 探针接管 8787 + 在 `setStatus` 里临时把状态写进本地存储 + 探测
  `connectSocket` 返回值的 `keys`/`typeof onOpen`，才拿到地面真相。

修法（`src/services/realtime.ts`）：
```ts
// ⚠️ 必须传 success/fail —— 不传 uni-app 就会把它 Promise 化，
// 得到的不是 SocketTask 而是 Promise，于是 next.onOpen 直接抛 TypeError
// → onLaunch 中断 → 整个实时通道的回调链没一个触发（实测坑过）。
uni.connectSocket({
  url: deps.url,
  success: () => {},
  fail:    () => {},
  complete:() => {}
})
```

mock 必须如实反映这个行为（`scripts/uni-mock.ts`）：`uni.connectSocket()` **必须**返回 `Promise`（reject 一个
失败原因），传了 success 回调才返回 `SocketTask` —— 否则下次还是会漏。
